# Target Pi evidence procedure

Status: NOT EXECUTED. Target is user-reported Debian 13 trixie, not the Windows host test environment. Record date, operator, Pi model/architecture, source commits, wiring revision and exact commands/results. Keep outputs safely isolated from active plant operation; test on a controlled bench with independent hardware protection. Named subteam assignments are not required by this package.

1. Record `cat /etc/os-release`, `uname -a`, Python version, application commit, package versions, `systemctl cat hmi.service` and `systemctl status hmi.service`. Compare the unit, install and model paths with CONFIGURATION_DEPLOYMENT.md. Verify trixie camera/GPIO dependencies rather than assuming Raspberry Pi OS apt guidance applies.
2. Record `ss -ltnp`, expected TCP 5000 binding, network exposure, user/group access (`id germ`), serial device identity and image/data path ownership. Check GPIO/video/dialout permissions as the service user. Record absent devices explicitly.
3. Run host checks first. Start exactly one service/camera owner; capture journal logs and camera acquisition errors. Verify valid/missing/stale sensor display, actual installation locations and calibration; do not call unavailable devices healthy.
4. With outputs in a known safe bench state run `python verify_live.py` from the installed application. It sends only OFF commands. Save JSON/log output and independently measure load de-energization; firmware_confirmed and reported_state are not physical feedback.
5. In a controlled setup, energize only approved bench loads, remove controller communications and measure the firmware >=10 s watchdog behavior. Separately verify hardware E-stop <=1 s, door <=0.5 s, leak <=2 s and no automatic restart after reset. Missing approved signal wiring or state manager blocks these acceptance claims. The communications watchdog cannot satisfy all safety deadlines.
6. Stop/restart the Flask service and power-cycle only under the bench procedure. Record startup time (SR-AUT-02 <=2 min), pump inhibition, profile/data retention and explicit restart. Current code lacks required interlock authorization; record failure/unavailable, never inferred pass.
7. Disable external network access while retaining local kiosk use. Exercise local controls, capture, alerts/history, ML and logging where implemented. Record browser external requests, timestamps and unsent remote alarms. Re-enable and verify configured remote critical notification <=5 min. Stubs do not pass these production behaviors.
8. Capture image/hash/SQL row, force SQL unavailable and disk-full on disposable storage, and restart the service. Check one camera owner, retained local JPEG, error status and recovery indexing. Do not fill production disk.
9. Once production SQLite/logging exists, record schema version, WAL/FULL/FK/busy timeout, concurrent reads/writes, restart integrity, consistent backup plus clean-location restore, linked images/hashes and CSV export. Fixture-only database success does not pass this step.
10. Run requirement campaigns separately: 90-day retention calculation, 80% warning/pruning with >=30 days images, 72 h unattended logging with <1% missing scheduled records, <=2 s data-to-visible refresh, local model latency/size/accuracy, and novice-user workflows. Link reports to REQUIREMENT_TRACEABILITY.md.

Evidence template: case ID; requirement; preconditions/devices; source/config versions; procedure; expected; actual; timestamps/latency; file/log/hash links; pass/fail/not executed; limitations. Review contracts and attach evidence before closing Baseline Gate. A failed or unexecuted hardware case must remain visible.
