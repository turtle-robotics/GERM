## Offline service graph and conservative lifecycle

`HostLifecycle` explicitly owns one marked host workspace and one core worker, with an OS file lease. Default application import still starts no hardware, workers or configured data services. The optional `offline_host.py` launcher binds only `127.0.0.1`, has no host/network exposure option, uses a pure synthetic STATUS/OFF adapter, no sensor provider, no camera or model and leaves the POST authorizer unset. No environment/HTTP flag can select physical interfaces. The earlier unmanaged `start_simulation_workers` entry point now refuses operation rather than creating unowned acquisition loops. M1 gateway/permission code is unchanged.

Startup order is explicit: synthetic gateway → verified M2 SQLite repository → M2/M4 restart/grow recovery → initial M3 durable logging → explicit synthetic sensor provider state → injectable M5 camera/local-ML adapters and journal recovery → M6 history/export → M7 backup → owned worker. HMI rendering is independent and can explain missing/degraded dependencies. The default synthetic adapter never emulates an energizing command; only STATUS/OFF acknowledgement is available. Trusted tests may inject separately labelled synthetic adapters/providers. Gateway reuse across startups and ML service reuse with an old capture owner are refused. Camera and ML retain their existing synthetic/local manifest contracts; no models are downloaded or inferred healthy by default. Missing sensors/camera/model remain unavailable/degraded, never fabricated measurements.

Initialization requires an explicit new workspace with `HOST_SIMULATION.json`; an unmarked pre-existing DB is never adopted or overwritten. Once marked, a missing/corrupt DB causes degraded recovery and is never silently recreated, even if the first launch used `--create`. The lifecycle keeps its lease through failed startup until explicit stop/recovery. Duplicate instances/starts fail; a worker with stale heartbeat or an observed exit causes a latched service fault and gateway inhibition. Readiness is distinct from lifecycle `running`: optional adapters and required input gaps can make readiness degraded while local history/HMI still work.

Startup/recovery creates a fresh gateway, discards confirmations/authority objects/old sensor health and preserves M2 durable profile/maintenance/E-stop restrictions. M4 recovery pauses any previously running cycle, clears armed/grant state and requires a separate confirmed Start with current inputs. M5 persisted capture schedules keep generation/anchor/claims/clock guards but acquire an additional host restart hold. Only explicit capture reconfiguration after startup can lift that hold; M5 future-boundary/clock-fault checks still apply. Automatic catch-up or resumption is not introduced. The worker may tick an actuator schedule only after an explicit M4 arm and current M1 permissions; every actual command still passes the existing gateway. No scheduler path reaches an adapter directly.

The owned worker checks the DB, checkpoints/drains M3, obtains only explicit synthetic input samples, polls synthetic controller STATUS through M1 and runs permitted scheduling/outbox work. A required DB/logging/worker failure latches degraded state, invalidates startup/confirmations and requests STOP through the gateway; it never retries itself into permission. Optional camera/model failures stay explicit and cannot diagnose a plant. Host recovery POST accepts only `{}` and reuses the existing simulation/authorizer/token restriction. It does not accept paths, permission flags, production settings or adapter selections.

Shutdown first inhibits/revokes and requests central STOP, then stops the core worker and waits for request/job/media quiescence. Data-mutating HTTP requests hold a lifecycle lease; while recovering/stopped, new data mutations are refused. Actuator/STOP/confirmation paths retain M1's boundary rather than being wrapped in a new dispatcher. Busy requests, inference/capture workers, exports or backups keep ownership and produce an explicit shutdown-waiting state; another runtime cannot start over them. Completed resources close in reverse order and configured services detach. Clean logging flush can fail and remains queued/error under M3; no unconditional persistence claim is added. Actual process death leaves M6/M7 running receipts for existing interrupted-on-startup recovery; files alone do not confer completion or runtime activation.

## Offline HMI and usability

All seven screens and prior navigation remain. Assets are same-origin files; CSP restricts connect/font/script/image origins to local resources (legacy inline script/style allowance is retained, not claimed as security certification). API responses are no-store. Runtime does not need internet, a cloud API, CDN, DNS or remote inference after dependencies are locally installed. No service worker or health/permission cache is added. Local Flask/loopback availability is still required to load pages: loss of that connection is distinct from loss of internet. Browser tests block every external origin and still exercise every screen; a separate full browser transport-loss simulation proves current status becomes unknown, commands disable and reconnect never replays POSTs.

The local service summary and optional details expose running/recovering/degraded/unavailable/stopped dependencies, current adapter/worker health and recovery guidance. Missing runtime is labelled unconfigured, not healthy. Sensor/camera freshness remains M1/M5-authoritative; stale camera images are hidden and no placeholder is substituted. A failed state poll clears the cached client permission/status reference and hides the camera. Recovery confirmation explicitly says permissions are discarded and schedules require separate action. Safe Stop/actuator requests retain their original server behavior.

Usability changes add a keyboard skip link, main focus target, current-page indication, visible focus, Cancel-focused/described command dialog with Escape cancellation, larger controls/touch targets, readable text, wrapping toolbars and scrollable content at 739×447. No claim of full accessibility conformance or novice acceptance follows from scripts. Recovery/status details are collapsible so established workflows and all seven screens remain available. Native browser confirmations retain keyboard handling. Error/loading/empty states remain explicit, and durable versus queued records are unchanged.

## Tests and limits

New host tests cover dependency order, no outgoing sockets/HTTP during runtime, marked/unmarked/missing/corrupt DB handling, duplicate owners/workers, detected/stale worker failure, blocked worker/request/job shutdown, logging/DB failures, current-to-stale synthetic inputs, missing camera/model, repeated restart/history/authority preservation, camera schedule restart holds, interrupted job receipts and production denial. Browser tests cover all seven screens with external origins blocked, local assets/CSP, no horizontal overflow, keyboard focus/navigation, Cancel/Escape without dispatch, touch size, local connection loss, no POST replay, explicit DB/core-worker recovery, paused/unarmed restart and stale images. Existing C++ and M1/M4/M5/M6/M7 suites remain required. [Evidence](../evidence/m8/README.md) records exact SHA, commands, dependencies, source/log hashes, CI and screenshots.

Open limits: Flask singleton/global injection is a single-host application, not a multi-tenant server or production authentication boundary. Read-only status observes worker health; host/Python hangs can delay watchdog processing, so no real-time or physical safety deadline is claimed. Some filesystem/SQLite/inference calls cannot be preempted; blocked owners remain held until completion/process exit. Sensor/adapter factories and authorizer are trusted Python code, not an untrusted plug-in sandbox. Installation/wheel/browser availability and target OS/system services are separate deployment gates. Offline browser shell caching, unattended recovery, physical interfaces, external model validation and automatic retention are not implemented. The proposed retention policy remains unapproved and no historical deletion occurs.
