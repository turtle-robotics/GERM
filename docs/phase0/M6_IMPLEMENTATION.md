## History contracts and HMI

`HistoryRepository` uses read-only, query-only SQLite connections. Seven resources cover experiments/cycle profile snapshots, sensors/dictionary units and quality, images/capture claims/outbox, inference/model/policy provenance, actuator request/reported/firmware ACK/physical verification, maintenance and durable events. LEFT JOINs preserve legacy rows; missing source/model/experiment remains null or explicitly unknown. Rows from SQLite are committed; a pending media-outbox receipt stays pending and is not described as an M3 event commit. Volatile event queues are not included in durable history.

GET `/api/history/<resource>` accepts `experiment`, half-open `start_utc`/`end_utc`, exact resource `type`, sensor ID for sensors only, and a literal substring search. Text is bounded to 120 characters, duplicate/unsupported filters are rejected, parameters are bound. Search covers name/sensor ID/file path/classification/requested state/maintenance details/event payload respectively; SQLite lowercase matching does not promise general Unicode case folding. Type means experiment status, sensor quality, capture reason, predicted class, actuator ID, maintenance action or event type, respectively. A common type/search filter applies independently to each requested export resource.

Default pages contain 100 rows, maximum 500. UTC keys normalize to six fractional digits for correct chronological ordering across `Z`, explicit zero offset and variable microsecond precision; invalid legacy time has an explicit flag and sorts first without a date filter. Stable PK breaks equal-time ties. Cursors bind resource, filters, page size and initial insertion rowid high-water using a per-process HMAC. Edits/tampering or a process restart invalidate a cursor with 400; start a new search. New inserts above that high-water cannot shift subsequent pages. Mutable fields remain a bounded live view, not a cross-request snapshot. Read queries have a three-second SQLite progress deadline. Existing experiment/sensor/time indexes and migration 007 event/type/maintenance/actuator indexes aid filters; normalized ordering may require a bounded sort. The 100,000-row query-plan test proves indexed sensor filtering, not every possible filter/latency combination.

The existing Trends screen adds labelled search controls, scrollable literal-text results, keyboard submission, next-page controls, honest loading/empty/error states, snapshot export and verified download links. All seven screens and navigation remain. Failed reads clear prior result rows. HTML-like text is rendered through textContent. Export status uses queued/running/complete/complete_with_errors/failed/interrupted, with explicit image errors and SHA. A partial archive is labelled partial. Session storage retains the last job ID for status after reload; retry is explicit and bounded. No export action sends an actuator command.

## Export job, snapshot and format

`HistoryService` is explicitly constructed with the existing M2 repository, separate scoped image/export roots and software SHA/version, then injected as `app.config['GERM_HISTORY_SERVICE']`. It has no hardware/gateway dependency. Default application startup configures no service, reads no camera, creates no export workers or artifacts; unavailable GETs return 503. All export/retry POSTs reuse the unchanged application host authorizer, simulation check and token. Production POSTs remain 403. Read-only download does not enable any production control.

Migration 007 adds the durable job journal and indexes through M2's checksum, backup and integrity machinery. A DB-scoped OS advisory lock enforces one export owner, including across processes. The worker has its own lock, never the gateway/state lock. One job runs at a time; additional IDs receive busy without a new claim. A canonical UUID and normalized definition provide idempotency; reusing an ID with changed content is rejected. Startup marks queued/running jobs interrupted even if files exist. No file alone is a completion receipt. Explicit POST `/api/exports/<id>/retry` with `{"retry":true}` retains job identity and uses a fresh attempt directory; at most three attempts. Durable completion failure cannot produce a download URL; restart exposes interruption. Old stages are preserved.

The worker uses M2's five-second-deadline SQLite backup API and integrity/foreign-key verification. All selected tables, joins, dictionaries, model/policy/profile snapshots, migration hashes and pending/committed receipts are read from that single immutable read-only backup. Each export resource streams one sorted SQL cursor in batches of 500, avoiding repeated full sorts for large exports. New live writes/ACK changes cannot affect exported rows. JPEG storage is not transactionally snapshotted: bytes are separately checked against the selected DB row and only verified bytes are archived.

Format `germ-history-export-v1` contains `manifest.json`, UTF-8 `tables/<resource>.v1.csv`, unescaped canonical `provenance/<resource>.jsonl`, snapshotted dictionaries/manifests and verified `images/<experiment-or-unknown>/<id>_<sha256>.jpg`. Empty resources still have versioned headers. Column lists, counts, software identity, UTC snapshot time, schema/migration provenance, filter definitions, snapshot SHA and member size/SHA are in the manifest. The final archive SHA is outside the archive, in its durable receipt/download header. Missing numeric values remain empty with quality flags; typed negative numbers stay numeric. Raw source timestamps are preserved alongside normalized `history_time_utc` and timestamp-quality flags.

CSV uses standard quoting/newlines. Untrusted string values are NFKC inspected after leading whitespace/control/format stripping and prefixed with an apostrophe for formula prefixes (`=+-@`, tab/CR/newline variants). Typed numerics remain unchanged. Canonical raw JSONL preserves original text and provenance; CSV escaping is not silently treated as the original source text. Confidence never implies accuracy; synthetic classifications are not diagnoses.

ZIP64 is enabled with stored members to bound compression CPU. Generated names prevent archive traversal/collisions. Image paths reject traversal, absolute paths and symlink components; checked JPEG bytes must match snapshot SHA, byte size and decoded dimensions. Missing/corrupt/changing files are omitted with exact image ID/expected hash/error. Partial mode produces `complete_with_errors`; strict mode fails without a downloadable receipt. Before exclusive publication, every member/hash/count and the manifest are checked; the file and POSIX directory are fsynced. Download checks the durable receipt, bounded size and SHA and serves exactly those verified bytes, not a reopened path. No thumbnails/placeholders substitute for saved JPEGs.

Default quotas: 20 retained jobs; three attempts each; 200,000 total selected rows; 256 MiB per attempt's conservative byte budget (snapshot, staging and archive); 1 GiB retained export artifacts; 10,000 path entries; 60-second worker deadline, plus bounded M2 backup. Dictionary limits are 10,000 rows per dictionary and 8 MiB encoded. Downloads are bounded to 256 MiB. Failed/staged files count toward quotas; reaching a quota fails/busies explicitly and never deletes anything. POSIX exclusive publication retains a staging hard link, counted conservatively in future usage. Operators need a separately approved cleanup policy if retained artifacts fill quotas. There is no automatic retention, pruning or deletion.

Run `python pi_hmi/tests/run_host_checks.py --root-app --output build/m6-evidence` and the M1/M4/M5/M6 Chromium suites. M6 adds 25 tests covering 100,000-row queries/export, equal-time/microsecond ordering, insertion high-water, filter/cursor validation, concurrency, Unicode/CSV injection/raw provenance, consistent snapshots during new writes, units/quality/ACK/policy manifests, image corruption/missing/change, ZIP integrity/traversal, quotas/deadline/disk-full/partial archive writes, DB read/write/backup/completion failures, v6-to-v7 migration/verified backup, ownership, interruption/retry and production restrictions. Real target filesystem/power-loss, recovery from external snapshot restore, multi-user authorization and deployment remain review gates.
