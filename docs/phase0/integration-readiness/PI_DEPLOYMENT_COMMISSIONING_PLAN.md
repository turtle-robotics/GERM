# Controlled Pi deployment and commissioning plan — NOT EXECUTED

This document is a proposal, not an installer or permission to access/modify the Raspberry Pi. No SSH/terminal session, device, production data or service was accessed by this readiness task. Existing Phase 0 Pi observations are historical; current target OS/architecture, Python, storage, boot jobs, services, wiring and firmware are **not revalidated**. Require explicit [stage approval](APPROVAL_GATES.md) before any future inspection, copying, installation, service operation, reboot, physical connection or test.

The current accepted runtime is synthetic only. `deploy_to_pi.py` deliberately refuses deployment/firmware work; `get_serial` refuses physical ports; the offline launcher accepts only synthetic ownership and leaves POST authorization unset. Do not remove/bypass those guards, relabel physical adapters simulated, adopt test authorizers, stamp a simulation marker onto real/restored data, or reuse the legacy partial-file deploy loop. Production/hardware operation requires a separately authorized and reviewed implementation preserving the M1 boundary.

## D0 — approve release and inventory scope

Project/deployment reviewers approve exact code/tree SHA (after any separately authorized merge train), manifests, target/account/path/port, allowed operations, window, supervisor, abort/rollback authority and evidence location. Resolve branch/review deltas and CI requirements; host acceptance alone is insufficient. Approve a current read-only inventory procedure before inspecting target services, timers/cron/udev/boot jobs, device ownership, OS/CPU architecture/Python/package compatibility, filesystem/storage/free space, power/thermal constraints, current application/firmware versions and every data path. Do not infer current state from an open SSH terminal or the old audit.

Evidence: signed operation scope; current target inventory and time source; immutable code/configuration/firmware/model hashes (model may be explicitly unavailable); identified running processes/services and competing device owners; storage measurements distinguished from estimates; named rollback checkpoint and decision maker. Unknown target facts hold this stage.

## D1 — preserve existing deployment and data

Data/operations owners approve quiescence or application-consistent snapshot method before copying any live DB. Inventory original DB plus WAL/SHM semantics, images, manifests, logs, incomplete jobs, approved export/backup artifacts, configuration, dependencies and service/boot definitions. A SQLite database file copied without its transactional state is not assumed consistent. Use a reviewed consistent SQLite backup and verified image linkage, with complete scope/exclusions in the manifest. Create an off-device verified copy if authorized; checksums alone do not prove authenticity. Record capacity/reserve and fail-full behavior; no cleanup of history, staging files, exports or backups is permitted.

Preflight the snapshot offline: schema/ledger/checksum/integrity/FKs, image hashes/dimensions/linkage, source provenance and incomplete receipts. Unknown/drifted/future schema stops adoption. M0-era schema and root protocol-1 data are not assumed compatible. Migration/legacy conversion must be planned and separately reviewed on new copies; never migrate the original as a trial or silently recreate a missing/corrupt DB.

Evidence: full retained inventory and scope; SHA-256 manifests; verified DB/image package; independent verification/readback; source release/service/configuration copies; source data timestamps/clock state; restore test into a new isolated destination; all exclusions and partial/error states. Existing data remains untouched and is never replaced by a synthetic seed.

## D2 — isolated immutable staging, synthetic mode only

After installation authorization, prepare a new approved release directory identified by exact SHA, a separate new test-data directory and separate evidence directory. Do not overwrite existing code, DB, image or service directories. Approve an offline dependency bundle with versions, hashes/licensing and target architecture/Python compatibility; install only into a dedicated environment. No real camera/model download, serial/GPIO/CSI access or firmware activation. Use explicit absolute code/data paths and a complete reviewed manifest including all migrations, services, assets and templates; a legacy short file list is inadequate.

An approved staging account should have only its new workspace rights and no device access or production-data write privileges. Bind the synthetic service to an approved unused loopback port; do not change firewalls/bind addresses or add external access. Do not install/enable autostart/system services, stop a production service or reboot without that separate authorization. Current host launcher's POST controls remain restricted. Synthetic measurements/images must remain labelled synthetic and unavailable real adapters must remain unavailable.

Run preserved host checks and seven-screen 739×447 browser tests on the isolated target, with installed dependencies and internet unavailable as approved. Confirm default imports do not start devices/workers, single-owner leases, startup ordering, duplicate refusal, honest missing sensors/camera/model, transport loss, denied POST/firmware paths, queue versus durable persistence and conservative shutdown/restart. This is target simulation validation, not physical commissioning.

Evidence: approved stage paths/account/port, package/SBOM/hash readback, device-access denial, no-production-write proof, no network exposure, exact test commands/results/UTC/real duration, observed CPU/memory/storage/temperature only from approved measurements, and preserved old deployment/data hashes. No target measurements are fabricated here.

## D3 — optional service lifecycle proposal, still synthetic

Only after explicit approval, review a dedicated disabled-by-default service definition naming the exact immutable code/virtual-environment and separate data paths. Specify one owner/process; prerequisite filesystem/data/schema verification; logging and gateway readiness; optional adapters honestly unavailable; scheduling/history/export/backup startup order; restart inhibition and data/job quiescence. Prevent duplicate legacy boot jobs or acquisition loops through a reviewed coordination/change plan. Do not start/stop existing services merely because a new unit exists.

Propose least privileges, bounded resources, restricted filesystem/device access and loopback binding, but validate actual target service-manager support before selecting settings. An automatic service restart may restart the process only: it must not recover actuator authority, replay commands, rerun incomplete inference/exports/restores or resume schedules. Capture schedules require explicit reconfiguration and clock-fault recovery preserves future boundaries/claims. Approved service shutdown must inhibit first, request central STOP where applicable and retain ownership while jobs/IO remain active.

Evidence: separately approved service definition, target compatibility, boot/dependency/duplicate/crash/repeated-restart tests, permission-denial tests, blocked-job/shutdown observations, durable/incomplete receipts, clock rollback and explicit recovery traces. Native blocking IO and target advisory-lock/power-loss behavior remain measured gates, not assumed guarantees.

## D4 — reviewed physical boundary and isolated acquisition

Stop at G2 until a separately authorized physical-interface/runtime change is implemented and reviewed. Its contract must specify electrical pins/topology/polarity/voltage/PWM/timers, independent E-stop/door/leak/thermal reset behavior, sole serial/camera/sensor ownership, protocol/firmware version, command IDs/ACK matching, freshness/quality/clock rules, state permissions and fail-safe fault policy. Retain M1 as the only actuator command boundary across UI, schedule, mode, maintenance, STOP, upload and restart paths. Production identity/read-download/network boundaries require review; no test lambda/token or HTTP flag can grant real authority.

Electrical/safety personnel approve physically independent hazardous-load isolation before even USB/serial/camera/sensor attachment; attachment may power/reset a controller. Approved acquisition procedures first validate raw signal location, scaling/polarity, calibration and plausible/stale/disconnected behavior with loads isolated. Do not transfer synthetic sensor policies or crop timings into production. Treat output requests, firmware ACKs and independent physical measurements as distinct evidence.

Evidence: named G2 signoffs, as-built drawings/continuity/calibration records, independently verified isolation, approved firmware/protocol/hash without flashing unless separately authorized, reviewed software diff and host tests, actual sensor timestamps/quality/units, rejected command paths and supervised fault/restart traces. No energized actuator testing is implied by acquisition approval.

## D5 — supervised commissioning and real endurance

After G3/G4 approvals, execute only named procedures in the [40-SR checklist](PHYSICAL_INTEGRATION_CHECKLIST.md) and [operator acceptance checklist](../M9_OPERATOR_ACCEPTANCE.md). Qualified electrical reviewers first establish independent protection/cutoff/reset behavior; validation records actual cutoff latencies and measured states. Approve each load, calibration, crop setting, camera operation and model/dataset separately. A model may remain unavailable during sensor-only testing. Custom firmware stays denied pending its own safety review; flashing is a distinct explicit operation.

Capture source/API/DOM timing for all seven screens, confirmations/cancellations, unknown/stale data, service failures and recovery. Preserve REL-01/02; before reliance, obtain a captured cause/fix or explicit validation/safety disposition and supervision/abort plan. DB/logging/clock/input failures must not confer authority or silently claim a durable success. On any unexpected/unsafe output, lost interlock, corruption, leakage/overheating, exhausted quota or missing evidence, use the approved isolation/stop procedure, retain history and hold recovery for review.

Only after the preceding gates may a separately approved supervised run measure **72 real continuous hours**, actual scheduled mist/light operations, physical outcomes, temperatures/water reserve, warnings, data cadence/missing fraction, storage and interventions. Do not combine interrupted runs or accelerated clock advances into that pass. Fault/restart campaigns are separately scoped. Actual 60-day biological performance, 90-day no-replacement simulation, maintenance times and service-life substantiation remain separate requirements. Remote delivery/unsent alarms are currently unimplemented and need approved implementation or controlled deviation before their SR/production acceptance.

Evidence: named operators/reviewers, calibrated instruments, configuration and raw artifact hashes; real UTC/monotonic elapsed time; physical cutoff/ACK/request traces; all failures/refills/resets/interventions; missing-record calculations; calibrated sensor/optical/thermal/water measurements; image/model provenance and held-out metrics; novice user timing/errors; reviewed exports/backups and independent isolated restore readback. Scope-specific signed dispositions are required. No host-only result can fill a physical evidence cell.

## Reversal and recovery at every stage

Before an approved change record the old absolute code/configuration/data selections, unit/boot state, immutable hashes, backups and observed physical isolation. If staging fails, keep existing deployment/data unchanged and retain the failed stage. If an approved service transition fails, isolate hazardous loads, quiesce writers under the reviewed procedure and preserve a fresh copy of all post-change data and incomplete receipts before selecting a compatible prior release/configuration. Do not automatically start an old production service; it may itself need safety review.

Never point old code at a newer incompatible database, run a destructive down-migration, overwrite a live image/DB tree, clear stages/receipts or delete post-checkpoint history. Verify any restored copy in a new destination; current M7 restoration accepts current schema only and never grants runtime adoption. Older schema checkpoints require a separately reviewed version-compatible validation/adoption procedure. Keep all later records available for explicit provenance-preserving reconciliation. Restart remains inhibited with fresh inputs, paused schedules and no old confirmations. See [merge/data rollback proposal](MERGE_ROLLBACK_PROPOSAL.md).
