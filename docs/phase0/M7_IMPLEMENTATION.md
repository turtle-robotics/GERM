## Reused contracts and storage inventory

M7 reuses M2's consistent backup API, integrity/schema/migration helpers and scoped paths; M6's decoded JPEG/hash/size verification; and a shared `ArtifactJobs` runner extracted from M6. M6's definition, CSV/archive, job receipt, ownership, explicit retry, quotas and download contracts remain. The shared runner uses whitelisted separate journals/OS ownership locks for exports and storage, one worker per service and retained attempt files. M1 command/state/permission code is unchanged. No storage worker acquires the gateway lock or calls an actuator adapter.

Migration 008 adds `storage_jobs` under M2's checksum-ledger, transaction and pre-upgrade-backup discipline. M6's v6-upgrade test now checks the imported current schema version rather than a hardcoded former version; its row/backup assertions remain. New tests explicitly verify v7-to-v8 preservation and verified backup. `SQLiteRepository.validate_snapshot` is additive and read-only: current version, exact known schema, checksum ledger, SQLite integrity and foreign keys must all match. It never upgrades or repairs an archive DB.

`StorageService` is explicitly injected as `app.config['GERM_STORAGE_SERVICE']` alongside a configured M6 HistoryService and a disjoint scoped storage root. Default startup configures neither storage artifacts nor workers. GET `/api/storage` reports observed logical sizes/file counts for the live DB/WAL/SHM, images, export artifacts, M7 backup/restore/verification artifacts and known M2 pre-upgrade backups. These are scoped configured paths, not an exhaustive search for arbitrary external backups. Size sums are logical file sizes, not allocated blocks; retained POSIX hard links may count twice. Missing configured directories are reported absent, links/errors/scan truncation produce incomplete inventory, and failed DB reads leave estimates/jobs unavailable while observed filesystem data can remain available.

Hosting-volume total/used/free bytes and utilization come from `shutil.disk_usage`, with UTC observation time and a label that other applications contribute. At >=80% it reports a warning; it neither deletes data nor changes actuator permission. Backup demand is a separately labelled conservative estimate based on DB page count and indexed image lengths, not proof that the image files exist. Free space can change after preflight; actual writes can still fail, and no failure becomes permission or a completion receipt.

## Jobs, packages and verification

POST `/api/storage/jobs` accepts canonical UUID and a definition with kind `backup`, `verify`, `preflight` or `restore`; the latter three reference a known backup job UUID. Arbitrary upload/archive/live destination paths are not accepted. All POSTs use the unchanged trusted host simulation authorizer and X-GERM-Token restriction; production POSTs stay 403. GET job receipts are bounded by the configured service. Retry is explicit through `/api/storage/jobs/<request_id>/retry`, with the same definition/ID and a new attempt directory, maximum three attempts. Startup turns queued/running receipts into interrupted; a file or recovery marker alone never establishes durable completion. Incomplete/failed files remain. No automatic retry/catch-up or deletion occurs.

Backup takes one verified M2 SQLite snapshot, then reads every indexed image from that snapshot. The package `germ-backup-v1` contains `database.sqlite`, `images/<original-relative-path>` and `manifest.json`. Manifest provenance includes request UUID/attempt, current schema version, software version supplied by the host installer, UTC snapshot-completion time, original image UTC/source metadata, migration ledger, image rows, member byte counts and SHA-256. ZIP64 is enabled; stored members bound compression CPU. Snapshot DB includes all source tables, not just filtered exports. Source export/backup archives, unindexed/orphan/staging images and arbitrary external files are not included; they remain untouched. Source job receipts are historical metadata in a restored DB, not proof that those artifacts exist at its new location.

Every saved image must match decoded JPEG dimensions, SHA and size. Missing, corrupt, linked or changing image files prevent a usable backup: a diagnostic package/job is `incomplete`, with image errors, and has no download URL. A consistent DB snapshot does not transactionally freeze the image filesystem; verification checks the bytes selected against that snapshot. Later captures or DB writes do not enter the package. A completed backup requires re-reading/verifying the package before exclusive publication, file/POSIX-directory fsync and durable completion receipt. Final archive SHA is in the receipt outside the manifest.

Verification refuses missing/corrupt ZIPs, whole-file receipt SHA mismatch, expanded-size/member-count excess, missing/unexpected/duplicate/case-colliding members, absolute/traversal/backslash/colon/reserved-device paths, links, directories/encrypted members, incompatible schema, bad migration provenance, corrupt SQLite/FK relationships, mismatched image rows or JPEG bytes. The manifest hashes all other members, not itself. Verification DB extraction uses exclusive files in the owned attempt directory; it never opens an archive DB through migration. Checksums prove consistency, not authenticity/security certification. Only known durable package receipts can be requested through HTTP. A backup download is available only for a complete verified backup and serves bounded bytes whose SHA/size match that receipt.

## Conservative isolated restore

Preflight verifies the current package again, schema/FKs and free-space estimate. Restore repeats preflight independently even if an earlier preflight passed, then creates a fresh owned `restores/<job-id>/attempt-N/offline-restore/` directory. It copies whitelisted members to exclusive files without `extractall`, checks restored hashes/schema/FKs and writes a recovery report. Existing destinations fail; no overwrite, rename of a live directory, activation, gateway attachment or replacement of configured DB/image roots is possible. UI confirmation explains the new offline copy.

`RECOVERY_REPORT.json` states `runtime_attached=false`, `permissions_restored=false`, `restore_activation_allowed=false`, restart required, source snapshot identity and image count. Historical running cycle/job rows do not constitute active runtime permission. Runtime adoption is separately gated and must apply M1/M2/M4 inhibited startup/recovery; it is not implemented here. If interrupted before a durable receipt, even a fully copied offline tree remains an interrupted job. Retry preserves it and uses a new attempt. Partial copy, disk-full, schema mismatch and verification errors remain incomplete/failed and never silently become restored production state.

Default limits: 20 retained storage jobs, three attempts, 10,000 indexed images, 256 MiB conservative attempt byte budget, 1 GiB retained storage-artifact quota, 60-second operation deadline plus M2's bounded backup, 1 MiB free-space reserve; bounded archive expansion/manifest and 10,000-entry inventory (1,000 known migration backups). M6 has its own existing quotas. Quota/free-space exhaustion refuses work and retains data. Some filesystem/SQLite system calls cannot be preempted by a Python deadline; no target worst-case latency guarantee is claimed. Same-volume packages do not protect against physical drive loss; approved off-device storage/authentication/permissions and target filesystem/advisory-lock/power-cut/endurance tests remain unresolved.
