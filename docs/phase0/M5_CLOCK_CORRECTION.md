## Defect and corrected rule

The prior scheduler compared UTC against an in-memory `last_tick`. It returned on rollback without a durable fault latch. Restart lost the reference timestamp, and later time recovery could resume without an explicit recovery decision. The corrected scheduler records every scheduling observation in SQLite before any scheduled acquisition, including ticks without a due capture. Migration `006_camera_clock_guard.sql` adds a high-water timestamp, fault latch, resume boundary and claim-generation provenance; it does not alter or replace the accepted v5 migration or historical claims.

1. An observation earlier than the persisted high-water latches `clock_fault=1`. The high-water never moves backward. A fault remains latched across repeated ticks, recovered UTC, disable/enable attempts, journal recovery and process restart. No scheduled claim or camera acquisition is authorized while latched. Database errors also inhibit scheduled acquisition.
2. Only explicit authorized POST `/api/media/recover` with `{"recover_clock":true}` can acknowledge it. Empty-object journal recovery and normal startup cannot acknowledge it. UTC must be at/above the persisted high-water; otherwise the API returns 423. The acknowledgement itself starts no capture and changes neither generation nor anchor nor existing request IDs/statuses.
3. Acknowledgement commits a resume boundary at the first anchored slot **strictly after the acknowledgement/high-water time**. Before that boundary, scheduling remains inhibited. Repeated acknowledgements are idempotent and do not move the boundary or create claims.
4. At/after the boundary, only the current eligible anchored slot can acquire once. An arrival more than five seconds late records that current slot as missed; it never walks/backfills intervening slots. A unique persisted request claim prevents re-acquisition on repeated ticks or restart, including indexed/failed/missed/interrupted claims.
5. Occurrence UUIDs preserve the existing `capture:generation:experiment:UTC-slot` format. Generation, anchor, anchored-slot alignment and resume boundary are checked before claim; the clock/configuration is checked again after reading a frame and before metadata/file publication. A detected rollback during acquisition cannot index that frame under an invalid slot.
6. Reconfiguration cannot clear a fault. Disabling without changing its definition is allowed; enabling/editing requires clock recovery first. Subsequent definition changes use a future cutover, no earlier than any existing recovery boundary, to prevent a new generation manufacturing another acquisition in an already-observed slot.

Example (UTC anchor 00:00, hourly): after observing 00:30, a tick at 00:20 latches a fault. Ticks at 00:20, 00:30 or 01:00 stay inhibited. An operator acknowledgement at 01:00 preserves identities and waits until 02:00. A first resumed tick at 02:00 can capture once; a first tick at 02:00:10 records missed. Restart preserves the same latch/boundary/claims.

Existing schema-v5 databases are backed up and upgraded transactionally using M2. The new high-water is conservatively seeded from the latest durable scheduled claim creation/slot times across all statuses. Old versions did not persist every idle tick, so migration cannot reconstruct undocumented observations; this is stated rather than manufacturing history. New committed observations and faults survive ordinary process restart. A failed/unacknowledged SQLite write cannot be represented as durable; its tick performs no acquisition. Physical clock/power-cut/DB-restore acceptance remains outside host scope.

## Reporting and evidence

GET `/api/media` and `/api/state.media` expose `scheduling.state`, `inhibited`, persisted `clock_fault`, `high_water_utc`, `resume_not_before_utc`, `operator_recovery_required` and storage error. States distinguish clock fault, clock behind high-water, waiting for boundary, disabled, ready, unavailable and unconfigured. A read-only status can report UTC behind high-water before the next scheduling observation persists the fault; it does not claim healthy scheduling. Camera preview/manual capture and journal repair remain separate from autonomous scheduling. Scheduler-status inspection itself performs no camera read.

The Plant screen shows an explicit scheduling/inhibited indicator and an authorized clock-acknowledgement action. The acknowledgement message explains future-boundary/no-replay behavior. Preview reads are not scheduled captures and cannot create image claims. Model/actuator permissions are unchanged; no physical interface is enabled.
